  Tespit Edilen Zayıf Noktalar

  1. KRITIK — Exhaustive Return Check Yok

  fun max(a: int, b: int) -> int {
      if a > b { return a }
      // else branch yok — checker geçiriyor, runtime nil döndürüyor
  }
  var x: int = max(1, 2)
  print(x)   // çıktı: <nil>

  Checker bunu geçiriyor. Runtime'da fonksiyon nil döndürüyor, program sessizce
  çalışıyor. Java, Go, Kotlin bu hatayı compile-time'da yakalar. Bu,
  "güvenilirlik" önceliğimizle doğrudan çelişiyor — bir program type checker'ı
  geçse de runtime'da tanımsız davranış üretebiliyor.

  Nasıl savunulur? "Bu intended kısıtlamanın farkındayız. Düzeltmek için
  checkBlock'un non-void fonksiyonlarda her path'ın ReturnStmt ile kapandığını
  analiz etmesi (control flow analysis) gerekir — scope dışı tutuldu."

  ---
  2. YÜKSEK — Coercion Tutarsızlığı

  var a: int   = 5
  var b: float = 1.5
  var sum:  float = a + b    // OK — coercion çalışıyor
  var cmp:  bool  = a > b    // OK — checker geçiriyor (isNumeric kontrolü)
  var eq:   bool  = a == b   // HATA — "cannot compare int with float"

  +, -, >, < operatörleri int vs float karışımını kabul ediyor ama == ve !=
  direkt left != right (tip eşitliği) kullandığı için reddediyor. Checker'ın iki
   farklı mantığı var ve bunlar tutarsız.

  Nasıl savunulur? "== için coercion kasıtlı çıkarıldı — task
  karşılaştırmalarında yanlışlıkla int/float karışımını eşit kabul etmemek için
  konservative davrandık" denilebilir ama bu çok savunulabilir bir pozisyon
  değil.

  Gerçek düzeltme: EQ/NEQ case'i de typesCompatible kullanmalı:
  case token.EQ, token.NEQ:
      if !typesCompatible(left, right) && !typesCompatible(right, left) {
          return nil, fmt.Errorf(...)
      }
      return TBool, nil

  ---
  3. ORTA — var x: void Geçerli

  task build { timeout: 10 retries: 0 parallel: false }
  fun notify() -> void { run build }
  var x: void = notify()   // checker geçiriyor, çalışıyor
  print(x)                 // çıktı: <nil>

  void bir değer tipi değil, "değer yok" işaretidir. Ama typeFromLexeme("void")
  TVoid döndürdüğü için var x: void grammar'da ve checker'da geçerli.
  Java/C++'da void x derleme hatası.

  Nasıl savunulur? "VarDecl checkStmt'inde if _, ok := declared.(VoidType); ok {
   return error } eklenerek kolayca kapatılır — kasıtlı değil, eksiklik."

  ---
  4. ORTA — on_failure Hiç Tetiklenmiyor

  pipeline ci {
      stage build
      stage test
      on_failure { print(1) }   // asla çalışmıyor
  }
  run ci
  // çıktı: [run] build, [run] test — print(1) yok

  Checker on_failure bloğunu type check ediyor ama interpreter'da RunStmt
  pipeline'ı sadece stage'leri iterate ediyor, task'lar gerçek process
  başlatmadığı için "failure" simüle edilemiyor. Tasarım dokümanı on_failure'ı 
  semantik bir özellik olarak tanımlıyor ama runtime'da dead code.

  Nasıl savunulur? "Task simülasyonu scope dışında tutuldu. on_failure yapısal
  olarak doğru tanımlanmış ve type checked; tetiklenme semantiği (hangi
  koşulda?) uygulama scope'u dışında."

  ---
  5. DÜŞÜK — void == void Geçerli

  var eq: bool = notify() == notify()   // checker OK, iki kez çalışır

  EQ case'i left == right (her ikisi de TVoid) → hata yok, TBool döner. Semantik
   anlamsız ama crash yok.
